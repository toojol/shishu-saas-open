# 架构与设计取舍

## 结构

```
门里（管理端）   落秤（收银端）   看板（手机端）
        \            |            /
         ── 云端服务（模块化单体）──
              商品 / 采购 / 库存 / 促销
              合作方 / 财务 / 报表 / 设备
                     |
               数据库（按门店隔离）
```

本仓只开源其中**纯规则**部分，位于 `java/` 下的各个模块。这些模块：

- 不依赖数据库、Web 框架或 Spring；
- 每个公式都有对应的单元测试；
- 输入输出都是 `BigDecimal`、`LocalDate` 等基础类型或 `record`。

## 为什么规则要写成纯函数

- 收银、结账、报表、对账用的是同一套公式，避免各处各写一份导致口径不一致；
- 纯函数可以脱离数据库单测，改动时测试能快速给出反馈；
- 金额统一由 `saas-core` 的 `Money` 处理：2 位小数、HALF_UP。

## 促销计算顺序

整单结账按以下顺序生效：满减 → 券 → 满折满赠 → 整单优惠（F1）→ 积分。每一步都以前一步之后的金额为基数，最终的行净额用于销售统计与联营结算；整单优惠与满减、券等按行小计占比分摊到各行。

实现位于 `saas-promo`：`DealMath`（买赠、N 件 M 元、第二件折、第 N 件固定价、分类与全场折扣、满赠等）与 `OfferMath`（满减）。

## 金额与快照的约定

- 金额一律以元为单位，统一 2 位小数，HALF_UP 取整；
- 销售行在入账时快照商品名、供应商、扣点等，之后改档案不影响历史单据。

## 为什么不做微服务

单店或小集团的数据量与并发量都不大，单体加模块化的部署和排障成本最低。模块边界按业务划分（商品、交易、会员、报表、设备），将来拆分时边界已经清楚。
